# WP-JOURNEY-OUTCOMES — customer need and repeat demand

Sources: `uc-new:domain:journeys`, `uc-new:domain:substitution`, `uc-new:domain:workforce` and the design contact-centre section. An HTTP receipt, an answered phone, a bot answer and a resolved need are different states.

Optional `soc-outcomes-1`, `s.outcomes`, factory `socOutcomesKernel`, `SOC_OUTCOMES`, `src/game/46-outcomes.js`. Module ownership also includes `tests/outcomes.test.js` (AC-SOC-079–084) and outcomes-handoff.md. Parent owns shared dispatch/UI and source registers.

A need is keyed to tenant/person/case and has purpose, permitted channels, resolution criteria, attempts, effort, first-contact outcome, repeat schedule and an explicit resolution record. Configuration separately versions a fictional bot/workflow contract: supported intents, task success conditions, handoff destination, bounded attempts and retry interval. It must not use a model's confident prose as evidence. Use deterministic explicit failure conditions (missing task integration, unknown intent, stale customer context), not live AI or unseeded chance.

Expose pure `evaluate(s, interaction, context)` returning resolved/unresolved/escalate with reason. `settle(s, interaction, evaluation)` is called once on state advancement/dispatch to record an attempt with an idempotency key. Unresolved bot containment may schedule a bounded repeated enquiry or human escalation; do not count deflection as resolution. Technical failure and failed mandatory artefacts remain separate obligations even if the customer need was resolved. Repeats retain case/person/tenant, choose only permitted available channels, and increase effort without duplicating the original bill. Stop after a configured cap and retain exhausted state.

`advance(s, hooks)` emits at most the bounded due repeat arrivals through a parent hook; the hook must route through the canonical interaction path on the already cloned parent state. It never increments the parent clock. Need history is bounded, but unresolved active needs cannot be pruned to fake resolution. Read-only metrics include first-contact resolution, repeat contacts, effort and pending/escalated needs. Aggregate demand and detailed traces remain explicitly separate; this module must not manufacture aggregate income from diagnostic repeats.

Provide explicit configure and task-result commands for synthetic tests. Keep a successful reference solution plus meaningful failures: bot answers but task fails; unsupported intent escalates; cross-channel context loss costs extra effort; repeat has same case; duplicate settlement/advance cannot create another repeat; unavailable channel delays rather than loses the need; cap stops runaway callbacks; worker/save equivalence. Configuration fingerprints exclude attempt progress and metrics. No source completeness claim.
