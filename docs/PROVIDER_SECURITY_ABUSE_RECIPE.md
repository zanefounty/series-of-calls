# Provider SCRUB abuse recipe v2

This bounded scenario adds a paid-control proof recipe for the source-linked SCRUB goal. It remains separate from the v1 paid offer terms and preserves existing v1 plan receipts. The authored recipe is [provider-security-abuse.v2.json](../content/provider-security-abuse.v2.json); it points to the same source IDs as [the paid security terms](../content/provider-security.json).

The fictional packet batch is fixed at 7,500 packets per second. It exceeds the clean capacities of both offered plans (1,000 and 5,000 PPS) and remains below their mitigation capacities (10,000 and 50,000 PPS). These are scenario parameters, not real traffic claims or conversions of the original game's bandwidth labels. The SIP cases use the commissioned authenticated carrier peer: one rate-limit probe, one message one byte over the paid maximum, and one allowed INVITE. Native admission records must report the expected result and exact paid generation. The blocked destination requires a real call interaction whose actual `to` value is `+18005550199`; a reason code by itself is not evidence.

`abuseRecipe(state, customerId, childRoot)` is a pure scheduler input. It fails closed unless the three current paid control bindings, native generations, peer and required paths are ready. It returns the exact native command inputs, a blocked-destination dispatch request, and an eligibility predicate for a later autonomous Provider demand call. Native packet and SIP probes use empty positive second offsets; offset zero remains reserved for the real core outbound call. If that SIP bucket has no room for the call, wait for the next minute before scheduling the recipe. The demand call is not scheduled or created by this recipe. Completion evidence requires the ordinary Provider job, resolved case and actual core usage settlement.

The recipe key binds customer scope, recipe/terms versions and the ordered network/SIP/destination project IDs, plans and effective generations. A completed run is immutable and unique for that tuple. Root dispatch must retain failed attempts as visible outcomes and must not turn a replay into another paid operation or an award. The helper validates actual native event records, projects, ledger postings, interactions, Provider jobs, cases and settlements; serialized command intent alone cannot satisfy it.

Root dispatch supplies a root-scoped `providerSecurityPins` envelope (`version`, `eventIds`, `interactionIds`, `jobIds`, `caseIds`) after validating those references against actual retained Provider abuse runs. Native security state does not grant or author these pins. Once event pins are in use, the native pack adds `eventHistory:{version:1,prunedRanges:[[from,to],...]}` and keeps the 1,000-row event limit. At capacity it removes the oldest unpinned row; if every row is pinned, it refuses the event-producing operation with `SECURITY_EVENT_CAPACITY` before that operation changes native state. The range list records only IDs of events actually removed and partitions the complete sequence with currently retained IDs. A missing admission row may use exact range membership to preserve older legitimate settlements beside lower pinned event IDs. Legacy FIFO saves without pins/history keep their existing fallback. Silently dropping a referenced event or fabricating a gap marker invalidates the save. The helper exposes `pinnedEventIds(evidence)` for root integration; it does not mutate native pack state.

The focused helper tests execute the real native security commands and call-admission path. They do not establish an end-to-end Provider mission, autonomous delivery, paid claim or progression unlock. Those require the shared dispatch/browser integration and their own acceptance evidence.
