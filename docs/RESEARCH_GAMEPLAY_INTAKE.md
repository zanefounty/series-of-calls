**Disposition:** planning aid only. It triages 75 curated archive-gameplay candidates; it does not add missions, accept requirements, promote historical causes into facts, or claim implementation coverage. The catalogue retains 75 curated candidates from 83 raw notes. These local `ARCH-UC-*` IDs are research IDs, not requirement or acceptance IDs.

**Backlog gate:** the original full-plan/source obligations take priority. Do not select these archive candidates for implementation while required baseline work remains, unless the user explicitly reprioritizes it. This intake can clarify future candidates but does not itself change the delivery order.

## Continuation workflow

1. Select a candidate and reopen its original post plus the relevant reply/follow-up before writing a requirement. The catalogue URLs are pointers, not evidence of current product behavior. Preserve date, product/version context, author uncertainty, and whether the reported result was only an operator's observation.
2. Record the historical report as a narrow symptom/evidence claim. Keep a proposed root cause in a separate fictional-design note. `Confirmed` means a participant reported a diagnosis or result; it is not independently verified. `Proposed`, `Unknown`, and open investigations remain hypotheses.
3. Check the nearest existing mechanics below. Specify the missing behavior rather than relabeling a generic route, outage, or passing call as equivalent. If the behavior needs unsupported product internals, mark it deferred and identify the dependency.
4. For any selected scenario, define desired configuration, provisioning, effective state, and independently observed result. Add one meaningful successful configuration and one negative configuration that demonstrates the gap. Use synthetic tenants, people, numbers, carriers, and traces. Exercise the validated dispatch, save/restore, and worker path where applicable.
5. Only after review, create a versioned requirement and acceptance case with source provenance. Keep the source mapping unchanged. Mark implementation partial only against the exact tested behavior; never infer parity from a similar title or module name.
6. Preserve the original witty comparisons when adapting source rows, as required by this project. Keep humor aimed at configuration absurdity, never at people harmed by outages or emergency failures. The text-only narrative adaptations do not count as mechanic coverage.

Read each gap as the missing candidate-specific contract, linkage, or observable result—not as a blanket assertion that every nearby primitive is absent. For example, existing mailbox storage or generic forwarding does not establish an after-hours mailbox route, a handset message-waiting indicator, or a voicemail media-capture path.
