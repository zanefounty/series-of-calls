# Provider security incident dispatch

The paid security path now executes the versioned `provider-security-abuse-v2` sequence after all three independently funded controls finish commissioning. It submits four native packet/signalling commands through the shared dispatcher, then creates an actual forbidden-destination voice interaction. Provider players cannot inject arbitrary attacks or author the customer root. No attack creates a due customer job, retail revenue or progression reward.

An explicit destination-policy refusal is recorded even when no route grants reach to that public number. An allowed but unroutable number still fails with `NO_ROUTE` and creates no security admission or reservation. Ordinary routable voice retains its single admission, duration and once-only usage settlement.

`providerSecurityAbuse` version 1 stores one run per customer and paid control-generation tuple. Each run retains its exact versioned recipe, five native event IDs, blocked interaction/case and optional completed-delivery evidence. Completion requires an ordinary autonomous Provider voice job arriving strictly after the incident, with the actual case, resolved interaction and native settlement. The same pure scenario demand command now drives job creation and evidence validation: caller, destination, direction, requested duration, case index and arrival minute must match. Actual billed units must cover that duration and equal both the Provider usage and native settlement. The unpublished v2 draft’s fixed example destination/duration were corrected before publication; no deployed paid v1 terms change. Initial commissioning or blocked attempts alone cannot claim delivery. Existing saves acquire a new run only through later simulated time; restore never synthesizes earlier evidence.

Validation binds the recipe timestamp to paid commissioning, native event order/generations and the actual failed interaction. The core security trace carries the exact native event ID. The completed proof is historical: later ticks retain its original evidence without replaying attacks. Child `providerSecurityPins` are derived from parent runs and checked exactly; they retain actual native events, interactions/cases and Provider jobs. Native event retention stays capped at 1,000 rows, with exact recorded eviction ranges. A separate Lab copy removes Provider pin authority while retaining valid native history.

The selected customer/carrier/phone/access inspector presents observed protection, waiting for later ordinary delivery and later delivered service separately, with read-only technical details. All new visible strings use the existing six-dictionary system; non-English additions retain the documented English fallback.

AC-SOC-803 exercises the routing/policy distinction, worker equivalence and no duplicate admission. AC-SOC-804 exercises actual paid commissioning, attack dispatch, later customer delivery, retention through minute181 and Lab copying. AC-SOC-805 rejects invented versions, timing, duplicate runs, event substitutions and pin changes, then compares waiting-save worker continuation. AC-SOC-809 checks the two inspector states and rendering purity. These are bounded checks; final frozen-candidate and browser execution must be recorded separately.

Canonical SCRUB claiming, its useful paid unlock, stronger-attack/upgrade choices, broader source capacity tiers and final cross-mission acceptance remain pending. This incident path does not certify the complete security source catalogue.
