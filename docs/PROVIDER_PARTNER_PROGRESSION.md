# Provider partner service progression contract

`progress.goal.p5` preserves the source goal “Make 5 peering friends.” The fictional work-package contract requires five distinct, current product-service integrations. Each counted edge must have its own paid Provider acceptance, an accepted directional test bound to both deployed endpoint generations and versions, a completed real delivery, and a current MSP/integrator responsibility whose scope covers the tested bindings. Repeated tests, aliases, duplicate endpoint/feature directions and unowned edges count once or not at all. This adapter does not reinterpret the source reward as AUD or change the source disposition.

`SOC_PROVIDER_PARTNER_PROGRESSION.evaluate(state, hooks)` derives evidence only from the existing paid UC/CC and room-to-interoperability adapters. It does not accept caller-supplied partner rows or generic `products.test-integration` results. Its `count` is the number of unique validated endpoint/feature keys; `target` remains five. `validateEvidence` rechecks each retained native project, test, delivery and source scope before accepting a saved award. Current readiness and retained proof are evaluated separately.

Provider inspection and serialized workers now expose this measured count in the P5 readiness row; the goal overlay shows the unchanged five-integration target and the remaining unavailable paths. Incomplete counts neither grant a receipt nor unlock an award. The root dispatcher must pass only its private, state-derived hooks. The module accepts `hooks.forAdapter(state, customer, root, adapterId)` or equivalent `hooks.ucCc` and `hooks.room` objects. The UC/CC adapter needs `resourceReady(root, resourceId)`, `currentSupport(state, customer, root, project)` returning `{ready, scope:{projectIds,postingIds,resources}}`, and `currentBoundary(state, customer, root, project)` returning `{ready, scope:[{resourceId,contractId,generation}]}`. The room adapter needs `resourceReady(root, resourceId)`, `featureStatus(root, deploymentId, feature)`, and `meetingPath(root, from, to, profile)`. A top-level `observeResource(root, resourceId)` is forwarded to support validation. These hooks must derive answers from validated Provider responsibility, product, boundary and transport state; do not expose them as user-supplied evidence.

## Proposed next paid edge: workplace telephony to suite calling

Existing fictional product tariffs remain separate: `ms-workplace-calling` is A$2,100 setup and A$420/period; `cisco-suite-calling` is A$2,300 setup and A$450/period. These amounts are not inferred from the source-game reward.

Proposed edge acceptance operation: A$350 setup, A$60/period, seven work minutes, one engineer and one support person. It covers the ordered `telephony` → `multitenant-calling` direction, both phone bindings, effective identity and carrier dependencies, accepted directional test, and an ordinary completed call whose actual endpoint traces match the tested generations and versions. Completion must retain a current named support contract covering `phone` and the accepted endpoint scope.

The negative path must expose an unsupported endpoint version or unavailable directional codec/path; it must block the ordinary call, preserve the failed test, require quoted repair/rebase and a fresh explicit test, and then complete a new real call. Root dispatch owns the operation, quote and native path hook; this module must not manufacture that evidence.
