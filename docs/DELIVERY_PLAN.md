# Full-scope delivery plan

`maintenance/next-work.json` is the authoritative execution index. It preserves the eight existing stages and adds stable stage/family IDs, requirement scope, dependencies, acceptance, owner and closure rules. Its assignments do not change source meaning, requirement disposition, gate policy or readiness.

Run `python3 scripts/delivery-inventory.py --check` from the repository root. It is read-only: it validates one and only one stage/family assignment for each row in `spec/generated/requirements.json`, then reports current requirement and source-register snapshots. Unknown namespaces, overlapping assignments, duplicate requirement IDs, multi-source rows, missing assignments, malformed stages and unresolved dependencies fail closed. Source namespace rules live in the index so new generated source types require deliberate review. The 75 `research/archive-gameplay/` proposals remain outside the 4,787 core requirements until the documented intake and owner acceptance.

## Reading the reports

The inventory command computes current assignment and requirement status counts from generated registers. It does not edit those registers or infer closure. `STATUS.md`, `docs/DEPLOYMENT_REVIEW.md`, `evidence/acceptance.json`, `evidence/verification.json`, upstream records and readiness files have different dates and scopes; their stated totals are snapshots, not interchangeable live counters. In particular, 352 and 362 acceptance cases describe different recorded points, and the deployment review's 1,231 JavaScript tests used an external jsdom override rather than the locked baseline. Read each receipt's inputs and limitations. No stale summary is silently rewritten by this index.

No exclusions, source dispositions or gate changes are authorized by the delivery index. Full source completion, legal approval, provider certification and release readiness must remain unclaimed until their actual closure evidence exists.
