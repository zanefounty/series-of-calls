## Gameplay and testing patterns worth adapting

1. **Reference solution plus a failing shortcut.** `tests/scenarios-playtest.test.js` has a player-like plan for every handmade scenario, an expected win-day band, and a deliberately tempting shortcut that must fail. Some scenario plans also vary by seed. It adds targeted counter-strategies for the Gangnam scenario, so a balance regression cannot hide behind one canonical recipe. The helper `scripts/lib/scenario-ref.js` executes game actions and day ticks, rather than asserting a prebuilt result. Sources: [scenario playtest](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/scenarios-playtest.test.js), [reference player](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/scripts/lib/scenario-ref.js).

2. **Seeded, differential, replayable fuzzing.** `scripts/lib/route-fuzz.js` applies the same seeded action stream to a base page and the changed page, compares state/results after actions and day advances, and includes normal, sandbox, scenario, weekly, puzzle, architect and imported-save starts. `tests/route-fuzz.test.js` keeps a small fixed seed sample in the fast test suite; the standalone `scripts/route-fuzz.js` can run hundreds of games, resume from a seed or save, and writes the divergence seed plus recent moves. This is strong for deterministic equivalence during refactors, but its comparisons are scoped to routing semantics; it is not a generic product acceptance oracle. Sources: [fuzz test](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/route-fuzz.test.js), [fuzz driver](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/scripts/route-fuzz.js), [fuzz model](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/scripts/lib/route-fuzz.js).

3. **Generated challenge calibration.** Weekly scenario and puzzle tests require deterministic generation from the week/seed, a valid player reference, no immediate day-zero win, a bounded par/win, and rejection/regeneration when a candidate has no measurable goal or the reference cannot complete it. Committed challenge files are checked field-by-field and tampering is rejected. This tests generator quality as well as the published fixture and fallback. Sources: [weekly scenario tests](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/weekly-scenario.test.js), [weekly puzzle tests](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/weekly-puzzle.test.js), [challenge player](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/scripts/lib/scenario-bot.js).

4. **Change-specific branch and quote coverage for the pinned gameplay.** The pinned `#261` standard-router change affects every path that creates a POP: direct build, wave/link, dark fiber/own cable and consortium seat. `tests/pop-standard.test.js` checks exact cash charged against quote, UI display, model/count installed, the no-downtime condition, affordability/unlocked behavior and malformed/old-save cleanup. A focused test explicitly takes each changed construction path and checks the POP model/count; the consortium-seat offer is checked for the quoted POP price. Source: [pinned focused test](https://github.com/fjaeckel/seriesoftubes/blob/da1a4e2f3c9f7fac12c94eefb8d35bd6b1e4ae16/tests/pop-standard.test.js); [pinned mechanics](https://github.com/fjaeckel/seriesoftubes/blob/da1a4e2f3c9f7fac12c94eefb8d35bd6b1e4ae16/src/game/60-features/96-pop-standard.js).

5. **Save/import and persistence edge cases.** Upstream tests cover reload, old-save migration, large saves, compression, corrupted compressed payloads, browser quota failures, interrupted asynchronous writes not overwriting newer saves, plus a 400-day lifecycle and a large-network fixture. The fuzz runner can start from an exported save. These tests distinguish persistence from just comparing an in-memory state. Source: [persistence tests](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/persist.test.js), [save-size tests](https://github.com/fjaeckel/seriesoftubes/blob/b2366ed26018f957309292d04adf5d6e76a89c65/tests/save-size.test.js).

6. **Reference implementation for optimization correctness.** `tests/load-time.test.js` compares optimized diversity lookup, map geometry and land tests against plain/reference implementations over thousands of combinations. The test is intentionally expensive; it dominated this full upstream test run. It is useful when the intended behavior is equivalence, not for proving gameplay completeness.

## Applicability to SOC and narrow proposals

- **Already adopted:** SOC's `scripts/test.js` and `scripts/test-timings.js` implement the same upstream strategy: discover root test files, run them separately with explicit worker count, refresh timing estimates, and longest-first balanced shards. `tests/durations.json` exists. The current harness already addresses the major runner-scaling pattern; copying it again is unnecessary. SOC's root-only test discovery is fine for current layout; check for nested suites if that layout changes.
- **Already stronger for actual browser acceptance:** Upstream CI runs unit tests, build and translation checks but does not run a real-browser gameplay matrix. Its test harness uses jsdom; `playwright-core` is used in performance tooling. SOC has `scripts/browser-campaigns.js` and `tests/browser-campaigns-contract.test.js`, with 48 campaign profiles and desktop/mobile viewports, plus reporting/sharding. Historical SOC browser matrices have run; full browser readiness remains false for the changed current inputs. Keep the browser matrix and run it with a real browser when available; upstream does not supply that acceptance evidence.
- **Best adoption for gameplay changes:** For each adapted upstream mechanic, map its distinctive branches into a focused SOC scenario/test: successful configuration, a natural under-provisioned/invalid alternative that fails assessment, repair and recovery, exact quotes/cost/state evidence, persistence/restore, and an observable UI/control route. The pinned router-standard test shows the right branch granularity. Do not assert fidelity merely because a shared campaign suite passes.
- **Useful addition to SOC gameplay assurance:** Add seed-aware repeatable playthroughs only where the adapted scenario has randomized inputs. Keep a small fixed-seed regression set in normal behavioral tests and an opt-in soak/fuzz command with seed, save/input hash and recent-command replay in failure output. Add an explicit seeded same-input/same-output assertion. SOC's `scripts/lib/campaign-journey.js` already exercises all four tracks, jurisdiction/mode combinations, procurement through three billing periods/renewal, recoverable incidents, checkpoints, and an alternative voice/room path; its current reference recipe is deterministic and doesn't take a seed. This is good cumulative campaign coverage, while upstream's reference-versus-shortcut pattern would add a distinct behavioral discriminator.
- **Narrow runner opportunity:** no runner replacement is indicated. If runtime/CI balancing becomes a demonstrated problem, use existing upstream-style timing data to shard the **registered acceptance suites** as a separately reported plan, preserve exact per-case accounting/input hashes, and compare wall time before/after. Do not simply shard the evidence command or weaken release gates: `scripts/record-evidence.py` currently relies on one TAP stream and `scripts/verify.py` checks exact expected-case accounting. Avoid repeating the multi-minute broad suite just to refresh timings.
- **Remaining evidence gap:** no real browser run was performed in this survey. Upstream's passing jsdom/unit suite cannot close SOC's browser acceptance. No SOC test, evidence receipt, release gate or upstream disposition was changed.

## Active lease-revocation slice: concrete test shape

For the coordinator's lease-revocation-to-transport adaptation, use upstream's seeded/replayable driver pattern with a **separate small reference transition model**, since a source-vs-fork differential would flag the intended behavior change as a mismatch. Once the command/state contract is fixed, generate a deterministic trace of synthetic tenants/resources and lease events with a printed seed and last commands. Include expiry-boundary advances (`deadline - 1`, `deadline`, `deadline + 1`), renewal/revocation order permutations, duplicate/stale revoke attempts, and the same resource/lease identifiers under a second tenant. After every command, compare effective/observed transport eligibility and append-only lease receipts to the reference model; assert that commands against one tenant cannot change the other's lease or transport.

Take a canonical save at a mid-trace point, restore it, then feed the remaining identical commands to the original and restored states. Compare their canonical states and public transport observations at each checkpoint; include a revoke exactly at expiry and after expiry so restore cannot resurrect a lease. Keep one short fixed regression seed in normal tests and expose an opt-in longer soak count for local/CI diagnosis. On failure report seed, index, command tail, saved-state hash and first differing paths. This is a concrete independent differential plus long-play check, rather than merely rerunning existing suites. Actual commands/fields should follow the coordinator's accepted contract; this report does not assert names or implementation status.
